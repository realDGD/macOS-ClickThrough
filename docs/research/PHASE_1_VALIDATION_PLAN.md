## 1. 待回答的问题

1. 使用公开 API，在真实 mouse-down 到达目标应用前激活准确窗口，能否使首次操作执行，同时保留原事件？
2. AX 动作能否在后台完成关键操作？它在哪些操作上与真实点击不等价？
3. 无需先激活的 PID 投递是否有效，是否受浏览器版本、事件来源或窗口数量影响？
4. 激活后重新投递是否提高覆盖；新增延迟、事件状态和兼容成本是否可接受？
5. 在当前 yabai、skhd 和 Karabiner 配置下，以上候选是否损害原有行为？

“前台应用改变”“窗口获得焦点”“API 返回 success”“日志写入 focused”“CGEvent 已投递”都只是中间观察。**验收必须证明原本操作实际执行，且只执行一次。**

## 2. PoC 范围与实验纪律

PoC 仅包含可启停的实验入口、必要权限能力检查、候选路由切换、最小观测与验证靶标。先不实现菜单栏产品、配置面板、自动启动、应用白名单、业务按钮补丁、分发包或性能优化框架。

每个候选单独启用；先关闭本 PoC 测基线，再开启单一路线。每次记录系统 build、SDK、实际应用 bundle/version、PoC revision、权限状态、测试操作、目标窗口状态及其他工具状态。不能只记录应用名称。

必须由**真实鼠标或触控板**产生关键首次点击试次。通过 CUA、脚本、AX 或 CGEvent 生成的测试输入可以用来做序列测试，但应标记为合成输入，不能替代真实鼠标端到端结果。

所有目标是当前屏幕可见、可交互区域的后台窗口；不以点击被其他窗口完全遮挡的控件作为任务范围。区分“其他应用后台窗口”和“同应用非 key 窗口”。测试前不 hover 激活窗口、不做 Focus Follows Mouse，不以预先切换焦点来代替 first-click 测试。

目标应用只有在当前台基线操作本身成功时，才可用于评价候选。如果 ChatGPT 的复制在前台也失败，应记录为靶标前置条件失败，不能归因于候选。

## 4. 实验分组与停止规则

### P0：基线与最低必要观测

先测不启用引擎的实际行为：哪些控件原本就支持后台左键、哪些右键本来就能开菜单、同应用与跨应用是否不同。建立前台基线、后台基线及最小 AppKit/SwiftUI 正负对照。

观测比较 Session 与 Annotated Session 的事件类型、坐标、公开目标字段、flags、click state、event number；用系统 AX 命中与公开窗口命中交叉比较。仅监听或记录时不修改事件，也不激活窗口。

### P1-A：提前激活，保留真实事件

对同一个物理 down，分别比较：公开 NSRunningApplication 激活；目标窗口公开 AX main/focus/raise 能力；两者的最小组合。设置属性前查询是否可写，不设置无关控件焦点。每个变体独立记录，不同时堆叠多种措施掩盖失败原因。

保留原 down/up/drag 的通过路径，不重新构造点击。记录请求发出、回调返回、可观察的应用/窗口状态与业务动作先后。重点判断是否有“窗口激活了，但操作仍没执行”的试次。

禁止通过固定长 sleep 假装得到激活完成保证。若 AX 往返阻塞或导致 tap 超时，记录为该变体失败。若无法可靠保持原事件，不继续为其包装产品。

### P1-B：AX 语义动作

命中目标元素并枚举实际支持的 actions，分别验证 AXPress 与 AXShowMenu。不硬编码复制按钮名称、bundle ID 或网页结构。输入框的 AXFocused 不能算完成文本插入点定位。

先隔离验证支持控件的语义能力，再验证与物理 down/up 的关联。必须覆盖按下后拖出取消、按住、双击、带修饰键点击。若即时 AXPress 改变这些行为，则把 B 记录为局部能力，不能直接升级为全局核心。

对 unsupported、invalid element、cannotComplete、目标阻塞分别记录。**cannotComplete 不自动补击或重试**，因为动作可能已经执行。混合策略只有在能排除重复执行时才有资格进入 Phase 2。

### P1-D：无需先激活的 PID 定向投递

使用公开命中能力确定目标 PID 与窗口上下文，独立测试：原事件拷贝后投递；通过正式 CGEvent/CGEventSource 接口构造并投递的序列。两者来源和实际结果分别记录，不能混为“原生保留”。不伪造其他进程 PID 或硬件可信状态。

测试原应用仍后台时是否实际执行按钮、链接、输入框和右键菜单；同一 PID 两个窗口必须分别验证。对当前 Chrome 155 与新 Chromium 源码线索分开归因；不得为了满足源码条件先更换成开发版再宣称本机版本已经通过。

即使使用原 CGEvent 拷贝，投递仍是重新投递。点击后自动变前台也是可观察结果，不预设“无需先激活”必然意味着“动作完成后仍保持后台”。

### P1-C：激活确认后重新投递完整手势

只在靶标和观测已可用后做该实验。不得先放行原点击、再无条件补击。down、up、drag 归属于同一逻辑手势；明确来源标记、递归控制、目标生存期及队列先后。

实验必须检查：只吞 down 却放行 up、只补 down、up 先于补 down、drag 目标改变、click count 被重置、修饰键丢失、投递再次被 yabai 或自己消费。任何一个问题都不能由“按钮能点了”掩盖。

激活失败、命中不确定、目标关闭、权限撤销、队列异常时停止该试次并记录输入影响；不得把缓存事件随意投给当前前台应用。PoC 必须始终有可用的停止方式。最终恢复状态机留待 Phase 2 决策。

### P1-E/F：补充机制实验

E 为自有 AppKit/SwiftUI/Electron 正负对照，验证 first-mouse 策略和业务计数器，不修改第三方应用。F 仅研究已公开事件字段；没有可证实的路由契约时保持低优先级，不靠未公开数字字段或私有事件记录“补齐”结果。

## 6. 试次、观测与性能

初筛建议每个适用的目标/操作/候选单元 **20 次**真实输入；出现错误立即保留可复现条件。对主候选的关键复制、按钮、左右菜单和第三方工具共存用例扩大到 **100 次**并跨不同测试会话执行。这些是拟定的实验规模，尚未取得任何计数结果。

记录分母、成功、漏执行、重复执行、误目标、输入语义改变、跳过、不可测和靶标错误。100/100 也仅证明相应环境与试次通过，不证明所有应用普遍有效；输入来源、目标版本和场景必须随结果保存。

记录：

- 原始事件、候选输出事件及逻辑手势的对应关系；不记录普通键盘文本。
- tap 回调耗时、AX 往返、激活观察时间、业务动作完成延迟；统一单调时间基准。
- 延迟 p50/p95/p99 与最大值，和同目标前台基线/后台基线比较。
- 空闲及密集输入下的进程 CPU、测量区间、核心计量方式、内存和系统负载。
- tap 禁用、重新启用、错误次数和数据缺口；读取 tap 延迟统计的副作用。
- CGEventSource 的来源、local events filter 与 suppression interval；投递时真实输入是否受到影响，不能只看合成序列自身。

先报告原始测量，再在 Phase 2 确定产品预算。不得将人为固定延迟或猜测 CPU 数字写成测试结果。默认不订阅无关键盘/高频 mouse-moved，不以轮询悬停焦点获得成功；必要高频观测仅在独立实验模式下启用。

复制验收优先粘贴到专用靶标核对。记录期望标识、匹配结果或必要摘要，不把用户通用剪贴板内容写进运行日志。诊断 DOM 信任/用户激活只在自有测试页或明确的调试条件下进行，不向 ChatGPT 注入业务脚本。

| 中间观测 | 激活请求/状态、AX action 与错误、过滤/放行/投递次数、回调与业务时间点 |
| 验收 | 预期原操作、实际结果、成功/失败/跳过/不可测、动作次数、证据及剩余不确定性 |

人工确认、用户报告、截图、靶标计数器和引擎日志的证据等级分别注明。截图显示窗口前台或 API 日志成功，不能独立证明复制实际完成。

## 8. Phase 2 决策门槛

候选只有在核心目标真实执行、无重复/误目标、组合语义与工具共存可接受，并有实际性能数据后，才具备进入正式核心的资格。

| 决策项 | 需要的结果 |
| --- | --- |
| 核心 API | A/B/C/D 各自的真实覆盖与失败原因，不由“接口更底层”决定 |
| 混合策略 | 可解释的能力判定及不重复执行证据；不能靠 AX 超时盲目补击 |
| 状态机 | 是否吞事件、缓存、重投或处理手势；依据实际路由需要决定复杂度 |
| 兼容模式 | 重复可复现的具体限制；优先按能力/系统语义，避免业务按钮或应用白名单作为核心 |
| 无法解决的限制 | 如目标拒收、AX 缺失、窗口关联不足、平台权限限制；记录实测范围 |
| 分发与权限 | 候选真实需要的能力、沙盒边界、稳定身份和新安装结果 |

若只实现获得焦点、仅在自有靶标成功、遗漏 ChatGPT/某个浏览器/右键/yabai，或需要私有 API/关闭 SIP/修改目标应用，**Phase 1 不得标记为完整通过，也不得据此启动完整软件开发。** 可以记录“局部可行、核心条件未满足”并继续研究。

原始协议交付时 PoC 尚未开发；此后执行结果逐项更新于上表及运行记录。当前 Phase 1 仅局部验证，最终 API/混合策略/状态机/兼容模式未确定。
