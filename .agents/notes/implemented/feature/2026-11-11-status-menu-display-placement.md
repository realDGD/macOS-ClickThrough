# Agent Note: 本应用菜单跟随点击屏幕

Status: implemented

## Problem

多屏环境中，用户在非活动屏幕右键菜单栏图标，ClickThrough 的菜单可能出现在另一屏；退出 ClickThrough 后，其他应用仍出现类似现象。原生状态按钮的菜单锚点不能作为本应用多屏定位的可靠依据。首个按全局鼠标位置弹出的候选解决了本应用的屏幕选择，但外接屏出现遮挡菜单栏的问题。

## Decision

仅对 ClickThrough 自己的右键菜单增加“右键菜单跟随点击屏幕”设置，默认开启；旧设置缺少该字段时按开启迁移，保留其他偏好。关闭后恢复系统状态按钮的原菜单定位；无法计算锚点时也使用该路径。选项独立于 A4 引擎开关。

开启时捕获鼠标的全局位置，选择点击所在屏幕，用公开窗口层级／边界读取实际菜单栏下缘；缺少该信息时使用可见区域及屏幕安全边距、状态栏厚度。菜单使用屏幕坐标弹出，并通过 NSMenuDelegate 的 confinementRect 限制在菜单栏下方。内部几何计算单独测试，不按活动屏幕、主屏幕或固定菜单栏高度选择锚点。

不改变其他应用的菜单、不提前切换屏幕焦点，不修改 A4 顺序、事件放行、窗口命中或 AX 超时。菜单左键继续切换引擎，右键继续提供设置与退出。

## Alternatives considered

- 继续完全依赖状态按钮的系统定位：保留为可选关闭路径，不能解决已反馈的跨屏定位。
- 直接使用鼠标位置：屏幕选择改善，但鼠标仍在菜单栏内，外接屏可能遮挡菜单栏。
- 使用统一高度或仅依赖 visibleFrame：本机只读检查中，状态栏厚度为 22 点，外接屏菜单栏窗口为 30 点；一台外接屏的 visibleFrame 还包含菜单栏，因此采用实际菜单栏边界并保留公开 API 退路。
- 全局激活另一屏以修正所有应用：没有完成可靠性验证，会改变焦点，超出本选项范围。

## Consequences

菜单仍使用原生 NSMenu。需要额外查询一次公开窗口元数据；屏幕边缘布局由 AppKit 调整，confinementRect 也是 AppKit 的布局约束，不能把几何测试等同于实际显示验收。

用户反馈首个候选能定位到点击屏幕，后续候选获用户认可并要求作为默认启用的可选功能；缺少独立截图及完整多屏物理试次日志，证据按用户反馈记录。具体检查与覆盖边界见[验证记录](../../../../docs/validation/STATUS_MENU_DISPLAY_2026_11_11.md)。
