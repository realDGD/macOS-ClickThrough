# Agent Note: 原事件放行后的有界 AX 诊断

Status: implemented

## Problem

间歇性多次点击才能激活的问题中，已有日志能看到 AXWindow 属性读取失败或 AXFrontmost 即时读回，却缺少命中元素的 role／subrole，以及原事件放行后的应用和窗口焦点证据。API 返回成功不能证明实际业务点击成功；读取失败也不能直接归因于目标应用。用户要求先补日志规则，保留详细开关及自动清理，不修改激活逻辑。

## Decision

详细模式为每次 down 生成 `click_id`，连接到达、跳过、AX 请求和后续采样。激活路径只保留已有命中元素及解析窗口的引用，记录已有调用的 PID、AXWindow 读取错误及返回类型；不在同步路径增加 AX 属性查询。请求前通过 NSWorkspace 读取前台应用元数据，精确的请求前焦点窗口明确记为 `not_sampled`。

原事件回调返回后，经过主队列的 150 ms 延后边界，在独立串行队列执行只读 AX 采样。记录同一引用的 role／subrole、目标应用 AXFocusedWindow、与命中元素／已解析窗口的 CFEqual 关系，以及已解析窗口 AXMain／AXFocused。分别记录前台应用、采样起止单调时间和实际延迟；不能将异步属性值当成点击当刻的值。

同时最多保留一组采样；忙时记录 `post_event_snapshot_skipped`，不排队积压。每次查询保持 25 ms 消息超时，累计 100 ms 后不再发起下一次查询，因此已开始的一次查询可能使总耗时超过 100 ms。错误、缺失值和预算耗尽显式记录，不用 false 代替未知。期间发生另一轮 down 时标记 `intervening_click`。

停止、失去监听或切换诊断级别使旧采样失效。已开始的有界只读工作可以结束，但结果丢弃，槽位直到完成才释放。关闭详细模式时不捕获 AX 引用、不安排新查询。

A4 的命中条件、AXWindow 解析、窗口 AXMain → 应用 AXFrontmost 顺序、失败返回、25 ms 激活超时和原事件返回不变。不会针对 AXWindow 命中增加 fallback、重试或重放。现有日志开关、持久化、2 MiB 轮换、7 天过期及 20 MiB 总容量规则保持原样；新信息仍只进入同一个本地日志系统。

## Alternatives considered

- 在事件回调内额外读取 role 和精确的前置焦点：能够更接近故障当刻，但会增加原事件放行前的 AX 往返，违反本次约束。
- 周期轮询并缓存前置焦点：缓存仍有时效误差，同时增加持续查询，本次保留明确的未知状态。
- 对每次点击无上限采样：可能在目标应用响应缓慢时积压和干扰输入，选择单槽并明确记录丢弃。
- 发现 AXWindow 读取失败后直接把命中元素当窗口：当前缺少故障时 role 证据，且属于激活逻辑修改，本次只收集证据。

## Consequences

详细模式增加有界的后台 AX 查询，可能影响目标应用的 AX 服务负载；关闭详细模式即可停止新增采样。日志不读取标题、正文、截图、剪贴板或键盘内容，也不序列化 AX 对象描述。AXFocusedWindow 是应用报告的状态，不是原事件实际投递、业务执行或窗口顺序的独立证明。后续点击、窗口销毁和属性不支持都可能使采样无法判定，需要结合时间及错误分析。单元、构建与 CI 检查不代表故障修复或真实鼠标验收。
