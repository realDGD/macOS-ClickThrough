# Agent Note: macOS 14 部署基线与图标兼容

Status: implemented

## Problem

最初按开发机将最低版本设为 macOS 27，但当前功能没有依赖 27 专属系统 API。用户随后明确要求降到 macOS 14，保持 A4 核心逻辑与测试范围不变。图标通过字符串加载，单纯通过编译不能发现旧系统没有新符号名称的问题。

## Decision

SwiftPM 和 Info.plist 的最低版本统一为 14.0；Homebrew Cask 使用 `:sonoma`。运行状态图标统一使用 `cursorarrow.click` 和 `cursorarrow.click.2`，保留原有字号和实际运行状态语义。Apple 系统符号元数据将这两个旧名称映射到 `pointer.arrow.click` 系列，因此新系统继续显示对应图标，无需在 A4 中增加兼容分支。

当前 `@Observable`、`@Bindable` 和设置窗口的 `NSApp.activate()` 都要求 macOS 14。SMAppService 要求 13。`pointer.arrow.click` 系列名称从 macOS 26 引入，对应的 `cursorarrow.click` 系列从 11 引入；图标兼容名称满足当前部署基线。

### 开发环境与后续版本决策

macOS 27 是主要开发与验证环境，使用当前适合的工具链和 SDK。macOS 14 是当前最低运行目标，开发工具和新功能 API 的选择按各自要求评估。

新功能优先研究现代公开 API。兼容冲突发生时，综合功能收益、受影响系统与用户、实现复杂度、维护负担、可靠性及验证成本，再决定以下路径：

- 新 API 带来明确收益时，可按系统版本提供功能，准确表达旧系统的可用范围。
- 兼容实现简单、可靠且成本合理时，保留最低版本并提供必要实现。
- 兼容成本或正确性代价过高时，记录功能收益和影响，单独决定是否提高最低版本。

最低版本 14 不等于每个未来功能都必须为旧系统提供回退；现代 API 也不自动成为提高最低版本的理由。版本限定或最低版本变更的长期取舍继续记录在 Agent Note，实际验证只覆盖相关改动，不自动扩大整个软件或系统测试矩阵。

## Alternatives considered

**维持 macOS 27。** 与本次明确的用户要求不符，也没有当前功能的 API 必要性。

**只改部署数字，继续直接加载新符号名称。** 字符串资源不会触发编译可用性诊断，旧系统可能缺少图标。

**按系统版本分支选择新旧名称。** 当前系统保留旧名称别名，统一名称即可覆盖目标范围，分支没有必要。

**继续降到 macOS 13。** 需要调整 Observation 状态管理和设置窗口激活调用，超出本次范围。

**把后续功能限定在 macOS 14 的 API 集合。** 这会限制以 macOS 27 为主的开发和新能力采用，因此采用逐项评估兼容取舍的政策。

## Consequences

支持目标扩大至 macOS 14+，A4 调用顺序、超时、事件与修饰标志政策保持不变。运行包仍只构建 arm64；Intel、macOS 14 实机行为、登录重启与撤权恢复未因配置降低而获得验收。

当前运行实例保留，新的候选包构建到独立目录。构建和验签结果、符号元数据、核心哈希比较见 [本次验证](../../../../docs/validation/MACOS14_2026_10_15.md)。
